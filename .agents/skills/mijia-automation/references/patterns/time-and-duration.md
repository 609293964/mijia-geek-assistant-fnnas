# 时间与时长模式

本文件是跨案例设计指导，不表示其中每个完整拓扑均已实机验证。具体运行结论以案例和实验的证据状态为准。

## 单次时长

```text
开始事件 → start = now()
结束/查询事件 → end = now()
durationMs = end - start
```

随后按需要换算分钟、小时和天。边界分段应先定义区间是否包含端点；不要先 `round()` 再用 60/1440 分段，除非提前跨档正是需求。

必须处理：重复开始、缺失开始、重复结束、重启、时钟回拨和负时长。

## 累计时长

```text
本次时长 = (结束 - 开始) / 单位
累计时长 = 累计时长 + 本次时长
```

需要去抖和状态机，避免功率在阈值附近反复结算。周期清零要定义跨午夜运行如何归属。

## 长周期提醒

时间戳差适合替代长时间 loop，但必须明确“起点代表什么”：初始化、上次提醒、上次确认还是实际维护事件。

提醒后自动重置起点会把“提醒周期”误写成“实际维护周期”。如果业务关心真实充电/保养，应增加用户确认或真实设备事件。

## 日期快照

```text
周期触发 → month()/date()/day() → 状态变量
业务事件 → 读取日期状态 → 分支
```

风险：零点任务漏执行、规则在月中启用、时区、跨月顺序和离线恢复。可即时计算时，不必长期缓存日期变量。

跨年月份范围使用“年末区间 OR 年初区间”；边界落在月中时必须同时考虑日期，不能只看月份。

## 节律和动态时间窗口

固定时间段和日出驱动的动态时间段都应先定义每段起点、终点和跨日恢复。日出自适应只说明时间起点变化，不等于读取环境光的闭环自适应。

- 规则中途启用时，优先按当前时间计算理论位置，不从陈旧变量继续累加。
- 每段结束夹紧目标值，并处理错过开始/结束事件。
- 验证时区、经纬度来源、跨午夜、夏令时和 `remaining > 0`。
- 家庭位置和作息只留在私有配置，不进入公开模板。

推荐执行顺序：

1. 计算当前所属时间段。
2. 根据当前时间直接计算理论值，不从陈旧累计值继续加：`progress = clamp((now-start)/(end-start), 0, 1)`，`value = startValue + progress*(targetValue-startValue)`。
3. 按目标设备 step 量化。
4. 使用 `min/max` 同时夹紧分段目标和 MIOT 范围。
5. 写入设备；到终点停止 loop。
6. 中途启用、错过边界或跨日时重新计算当前位置。

当前网关已验证 `month()`、`hours()` 可在运行时取值，且 `min()` 能将超调表达式夹紧到目标值；时区、跨月和完整全天曲线仍需验证。

## 状态持续与时间控制三层架构（工业级标准）

在实现“状态持续 N 秒/分后触发动作”（如有人超过 5 秒、门未关超过 30 秒、功率持续低于 5W）时，严格按以下三层架构选型：

| 层次 | 方式与典型结构 | 适用场景与优劣 |
|---|---|---|
| **Tier 1（设备原生属性）** | `deviceInput(no_motion_duration >= X)` | 设备 Spec 包含可通知的该属性且用户需求符合量程时必须使用；不要再叠加同一意图的 `statusLast`。固件层计时并上报，功耗最低，抗网关重启。 |
| **Tier 2（网关状态维持首选解）** | `设备状态判定 → statusLast(timeout: 毫秒) → 动作触发` | **秒级持续需求（5s/10s/30s）或无原生属性时的标准解！** 状态输入有状态监听，**若中途状态反转（如人离开）自动重置计时**，抗干扰极佳。 |
| **Tier 3（动作无条件延时）** | `事件触发 → deviceOutput(动作1) → delay(X) → deviceOutput(动作2)` | 仅用于动作发生后的无条件等待（如开灯后延时 10 秒关灯），**严禁用作状态持续判定**。 |

### ⚠️ 负向约束（严禁行为）
- **严禁**把“状态持续 N 秒”写成 `deviceInput(有人) → delay(5000) → deviceGet(有人?)`。这种拼接在人快速离开时依然会等待 5 秒再去查询，无法像 `statusLast` 一样实时复位，逻辑冗余且易产生竞态。

## 时间单位与量程对齐（秒 vs 分钟）

用户口语通常使用“5 秒/10 秒/30 秒/1 分钟”，但硬件属性在 MIOT Spec 中有明确的 `unit` 与 `range`：

1. **单位换算**：
   - 若 Spec 的 `unit: "minutes"`，用户需求为“120 秒”，必须换算为数值 `2`；
   - 若 Spec 的 `unit: "seconds"`，用户需求为“2 分钟”，必须换算为数值 `120`。
2. **秒级需求与分钟级硬件对齐**：
   - 若用户需求秒级（如“5 秒有人开启灯带”），而设备原生属性 `unit: "minutes"`（最小 1 分钟，`step: 1`）：
   - **禁止直接将 5 填入分钟属性**；
   - **标准方案**：采用 **`statusLast(5000)`** 读取设备的实时有人状态（`Occupancy Status = 1`），在网关侧进行 5 秒精准计时；
   - **硬件备选**：向用户说明硬件原生属性最小为 1 分钟，若需要可调整为 1 分钟。
