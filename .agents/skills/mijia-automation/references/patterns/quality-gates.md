# PAT-QUALITY-01：可用性优先与复杂度门槛

本文件把上游 Skill、Home Assistant 自动化文档和 Node-RED Flow 设计中的通用思想转换为米家极客版的设计检查。它不复制其他平台的 YAML、节点名或运行时语义；米家网关的实际行为仍以 MIOT Spec、图回读和运行证据为准。

## 目标

自动化首先要满足：

```text
能解释 → 能校验 → 能回读 → 能运行 → 能恢复
```

不能因为图保存成功、节点数量更多或方案看起来更“智能”，就认为规则可用。

## 默认复杂度预算

这是生成时的默认警戒线，不是绝对拒绝规则：

- 一个独立意图默认不超过 8 个执行/流程节点。
- 默认不超过 2 个状态变量或 register。
- 默认不超过 1 个 loop；没有明确停止条件时禁止生成 loop。
- 默认不超过 2 层条件分支；更多分支应考虑拆成独立规则或虚拟事件入口。
- 每增加一个变量、查询、循环或分支，都必须说明它解决的具体问题。

超过警戒线时，Agent 必须先做复杂度审计：列出新增节点的目的、状态生命周期、重入行为、停止条件和恢复路径。能拆分时优先按独立意图拆分，而不是继续向同一张图堆节点。

## 六个质量门

### 0. 先读当前状态，再准备写入

对于修改已有规则，先取得当前规则的 ID、名称、启用状态、完整节点图、变量依赖和关键连线，形成写入前快照。候选图必须基于这份快照生成，不能依赖旧消息、截图或记忆中的规则状态。

写入前至少比较：节点和循环数量、增加/删除的节点与连线、变量读写集合、启用状态以及关键设备引用。只有差异能够解释时才进入写入阶段。

### 1. 最小可执行图

先生成最短闭环：

```text
事件入口 → 必要状态/条件 → 一个动作终点
```

查询、变量、延时、循环和虚拟事件都不是默认组件。只有需求或设备能力明确需要时才添加。

### 2. 触发来源可追踪

多个事件入口合并时，必须能回答“哪个入口触发了哪条路径”。不要让多个入口共享一个无法区分来源的条件分支。需要区分来源时，使用独立分支、专用事件或变量记录来源，并在设计表中写明。

### 3. 重入策略明确

在上一轮还未结束时再次触发，必须提前选择一种可解释的行为：

| 策略 | 米家设计问题 |
|---|---|
| 忽略 | 是否允许新事件丢弃？ |
| 重启 | 是否应取消上一轮并从当前状态重新开始？ |
| 排队 | 网关是否有可靠的排队能力？没有证据时不得假设有 |
| 并行 | 多个动作是否会互相覆盖或产生竞态？默认禁止假设安全 |
| 合并/去抖 | 是否应通过 `statusLast`、状态变量或事件合并压缩重复事件？ |

米家 `delay`、`statusLast`、`loop` 的重入与复位语义不能套用其他平台的 `single/restart/queued/parallel` 名称；必须按当前网关实验结果表达。

### 4. 状态与范围最小化

局部状态只服务于一条规则时，优先使用规则变量；跨规则契约才使用全局变量。变量必须有初值、生产者、消费者、退出/清理路径和未知值策略。不要为了复用几张卡片，把所有设备都抽象成一层难以检索的全局变量。

多个独立意图驱动同一组设备时，各意图必须先维护自己的状态，再用明确的 resolver/汇总状态决定共享执行器是否运行。不要让一个意图直接把另一个意图的状态置零或置一，否则结束事件可能误停仍在生效的业务。

复杂逻辑可以抽象为“适配入口 → 核心逻辑 → 设备输出”，但每个适配入口必须可单独测试，核心逻辑不能依赖某个家庭设备的私有枚举。

### 5. 可验证和可恢复

创建前必须能给出：

- 静态连接和能力校验结果；
- 每条关键边的 `EVENT / STATE / QUERY` 语义；
- 网关保存后的完整图回读结果；
- 正常、重复触发、离线/未知、重启和人工操作路径；
- 失败后停止、保持、回滚或通知的行为。

如果只能证明“网关接受保存”，不能报告“自动化可用”。

试运行应在候选图或克隆图上完成，不能先修改真实规则再观察结果。保存后再次回读并比较关键图结构、变量引用和启用状态；回读不一致时报告“已提交但未确认”，不要自动重复写入。

## 拆分规则的信号

满足以下任一项时，优先考虑拆分：

- 一张图同时处理照明、离家、入睡、通知等多个独立意图；
- 同一变量被多个互不相关的业务写入；
- 一个 loop 同时承担轮询、重试、超时和恢复；
- 分支既判断设备状态，又记录行为来源，又做通知格式化；
- 无法在一句话中说清楚规则的入口、条件和终点；
- 需要依赖“某个节点先执行”但没有显式状态或连接保证。

拆分后的规则可以通过虚拟事件或明确变量连接，但必须记录事件生产者、消费者、有效载荷、重复事件和重启行为。

## 交付前快速审计

1. 删除任意一个节点后，能否说明哪项需求失效？不能说明的节点先删除。
2. 规则被连续触发两次时，会忽略、重启、合并、排队还是并行？
3. 设备无响应或查询值陈旧时，是否会误执行危险动作？
4. 重启后状态变量、循环和模式游标是否仍可解释？
5. 用户手动操作后，自动化是否会覆盖用户意图？
6. 能否拆成更小的规则而不增加隐式耦合？
7. 每个复杂结论是否有对应的实验或运行证据？

## 来源与边界

- `SRC-UPSTREAM-OH-MY-SAGE-001`：上游 Skill 的渐进检索、能力映射和证据升级方法。
- `SRC-HA-AUTOMATION-BASIC-001`：触发、条件、动作的职责分层。
- `SRC-HA-AUTOMATION-MODE-001`：重复触发时的忽略、重启、排队和并行问题分类。
- `SRC-NODERED-FLOW-STRUCTURE-001`：状态作用域、可读 Flow 和跨 Flow 连接。
- `SRC-NODERED-SUBFLOW-001`：用可复用子流降低重复和视觉复杂度。
- `SRC-LIXINYU-MIJA-SKILLS-001`：只读导出、候选图试运行、保存后回读和变量依赖审计。

这些来源只提供设计思想，不能证明米家极客版支持同名的运行模式或复用机制。
