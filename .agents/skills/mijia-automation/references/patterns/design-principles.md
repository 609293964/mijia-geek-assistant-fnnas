# PAT-DESIGN-01：从生活需求到可运行规则

本文件沉淀公开文章和既有案例中的设计思路，不复制具体设备、数值、截图拓扑或家庭习惯。它用于帮助 Agent 选择验证方向，不直接等同于网关协议或强制校验规则。

## 证据边界

- 主要来源是公开文章中的卡片说明和家庭案例，当前证据等级为 `public-article`。
- 文章中的设备型号、SIID/PIID、阈值、延时、变量名和节点数量不得直接复用。
- 只有经过 MIOT Spec、图差异、本地 mock、网关往返或实机运行验证后，才可把具体行为升级为更强的模式或 validator 规则。
- 本模式优先固化“如何思考”，不固化“某一张图应该长什么样”。

## 设计总线

任何新需求先拆成：

```text
入口事件 → 当前状态/查询 → 变换 → 条件 → 动作 → 退出 → 恢复
```

每条边都标记为 `EVENT`、`STATE` 或 `QUERY`：

- `EVENT` 表示一次发生，只负责启动流程，不代表状态仍然成立。
- `STATE` 表示可持续判断的结果，适合接入 condition 或逻辑状态节点。
- `QUERY` 表示流程运行时读取一次，可能受到缓存、离线和最近上报值影响，不能默认等于物理实时状态。

如果需求只有“发生一次”的入口，却要求覆盖“状态后来发生变化”的场景，应增加能够代表后续变化的事件入口，而不是重复堆叠同一个事件卡片。

## 六个决策原则

### 1. 先判断语义，再选卡片

“有人进入”和“有人持续存在”、“灯刚打开”和“灯当前开启”不是同一语义。事件触发、状态判断和查询分支不能互换；`condition.trigger` 负责什么时候检查，`condition.condition` 负责检查什么状态。

### 2. 持续状态与动作等待分开

- 状态必须持续为真一段时间：优先考虑设备原生持续属性，其次使用 `statusLast`。
- 动作已经发生，只需要等待后续动作：使用 `delay`。
- 不要用 `deviceInput → delay → deviceGet` 伪造状态持续；这条链在状态中途反转时可能仍然继续执行。
- 延时、持续、循环的重入和复位语义需要单独确认，不能只因为名称相似就互换。

### 3. 状态必须有生命周期

每个自定义状态或变量都要写清楚：

| 项目 | 必须回答的问题 |
|---|---|
| 初值 | 首次启用、重启、断电后是什么值？ |
| 写入者 | 哪些事件或动作可以改变它？ |
| 读取者 | 哪些规则依赖它？是否允许陈旧？ |
| 结束 | 什么时候清零、退出或重新武装？ |
| 异常 | 设备离线、事件丢失、重复事件时怎么收敛？ |

没有退出或恢复路径的“模式变量”不能直接作为全局事实使用。

### 4. 记录行为来源，避免自动化覆盖人工操作

当需求同时包含“自动打开后自动关闭”和“人工打开后保持开启”时，必须记录行为来源或自动化锁定状态。最终动作不能只读取灯的当前值，否则无法区分人工操作、App/语音操作和自动化操作。

该原则可扩展到亮度、色温、模式和窗帘位置，但具体来源识别能力必须依据设备事件和网关运行证据确认。

### 5. 设备不支持时增加适配层，而不是猜字段

如果设备能在米家 App 中工作、但没有可供中枢触发的属性或事件，可以考虑：

```text
外部入口/App 自动化 → 虚拟事件或桥接变量 → 极客版核心逻辑 → 设备/通知输出
```

适配层要说明数据方向、更新时机、重复触发、丢事件和未知状态。不得把“App 能控制”推断成“中枢有同样的 MIOT 能力”。

### 6. 复杂度必须有收益

只有在简单规则无法表达需求时，才引入变量、循环、查询、状态机或多分支。引入前说明它解决的具体问题：

- 设备替换：是否确实需要适配层？
- 多意图竞争：是否需要优先级仲裁？
- 无触发能力：是否必须周期查询？
- 状态恢复：是否需要持久变量？

如果只是为了让流程“看起来完整”，不要增加节点。优先生成最短可验证路径，并将复杂扩展作为后续版本。

## 方案检查表

设计完成、能力校验之前，逐项回答：

1. 真正的入口是事件还是状态变化？
2. 若状态已经成立，后来另一个条件变化时，规则还能被触发吗？
3. 每个 `condition` 的 trigger 和 condition 是否分别有正确来源？
4. 使用的是设备原生时长、`statusLast`、`delay` 还是循环？为什么？
5. 状态变量是否有初值、写入者、退出和恢复？
6. 是否需要区分人工、App、语音和自动化造成的设备变化？
7. 设备能力不足时，是否需要虚拟事件或桥接变量？
8. 查询值可能陈旧或未知时，是否有保守分支？
9. 循环是否有停止条件、最大次数、频率上限和重启行为？
10. 删除一个变量、替换一个设备或禁用一条规则时，依赖是否仍可解释？
